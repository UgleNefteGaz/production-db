# Триггеры и межтабличные бизнес-правила

## 1. Назначение документа

Документ описывает триггеры, используемые для реализации бизнес-правил, которые нельзя корректно выразить через обычные ограничения `CHECK`.

В PostgreSQL триггер состоит из двух частей:

1. триггерной функции `RETURNS trigger`, содержащей бизнес-логику;
2. объекта `CREATE TRIGGER`, который определяет, при каком событии и для какой таблицы должна выполняться функция.

Триггеры проекта реализованы в файле:

```text
sql/triggers.sql
```

Всего создано 6 пользовательских триггеров.

## 2. Контроль суммарного количества партий заказа

### Триггер

```text
trg_check_batch_planned_quantity
```

Таблица:

```text
production_batches
```

События:

```text
BEFORE INSERT
BEFORE UPDATE OF production_order_id, planned_quantity
```

Триггерная функция:

```text
check_batch_planned_quantity()
```

### Бизнес-правило

Суммарное плановое количество всех производственных партий заказа не должно превышать:

```text
production_orders.planned_quantity
```

Например:

```text
Заказ = 1000

BATCH-001 = 500
BATCH-002 = 500
```

Попытка добавить:

```text
BATCH-003 = 100
```

дала бы:

```text
500 + 500 + 100 = 1100
```

что превышает план заказа.

### Проверенные сценарии

Проверено:

- добавление новой партии сверх лимита;
- увеличение `planned_quantity` существующей партии сверх лимита.

В обоих случаях операция была отклонена.

## 3. Запрет уменьшения заказа ниже суммы партий

### Триггер

```text
trg_check_order_planned_quantity
```

Таблица:

```text
production_orders
```

Событие:

```text
BEFORE UPDATE OF planned_quantity
```

Триггерная функция:

```text
check_order_planned_quantity()
```

### Бизнес-правило

Плановое количество производственного заказа нельзя уменьшить до значения, которое меньше уже распределённого количества по партиям.

Например:

```text
BATCH-001 = 500
BATCH-002 = 500

Сумма партий = 1000
```

Попытка установить:

```text
production_orders.planned_quantity = 900
```

должна быть отклонена.

### Проверенный сценарий

Попытка уменьшить заказ с `1000` до `900` была успешно заблокирована.

## 4. Запрет дефектов для успешной проверки качества

### Триггер

```text
trg_check_defect_quality_result
```

Таблица:

```text
defects
```

События:

```text
BEFORE INSERT
BEFORE UPDATE OF quality_check_id
```

Триггерная функция:

```text
check_defect_quality_result()
```

### Бизнес-правило

Если результат проверки качества:

```text
Passed
```

для неё нельзя регистрировать дефекты.

### Проверенный сценарий

Попытка добавить дефект к существующей проверке со статусом `Passed` была отклонена.

## 5. Запрет Passed при наличии дефектов

### Триггер

```text
trg_check_quality_passed_without_defects
```

Таблица:

```text
quality_checks
```

Событие:

```text
BEFORE UPDATE OF result
```

Триггерная функция:

```text
check_quality_passed_without_defects()
```

### Бизнес-правило

Проверку качества нельзя перевести в статус:

```text
Passed
```

если с ней уже связаны записи в таблице:

```text
defects
```

### Проверенный сценарий

Попытка изменить существующую проверку с дефектами на `Passed` была отклонена.

## 6. Контроль времени проверки качества

### Триггер

```text
trg_check_quality_check_batch_period
```

Таблица:

```text
quality_checks
```

События:

```text
BEFORE INSERT
BEFORE UPDATE OF batch_id, checked_at
```

Триггерная функция:

```text
check_quality_check_batch_period()
```

### Бизнес-правило

Время проверки качества должно соответствовать периоду выполнения производственной партии.

Должно выполняться:

```text
checked_at >= started_at
```

Если партия завершена:

```text
checked_at <= completed_at
```

Также нельзя регистрировать проверку качества для партии, которая ещё не была запущена.

### Проверенные сценарии

Проверено:

- попытка создать проверку раньше `started_at`;
- попытка создать проверку позже `completed_at`.

Обе операции были отклонены.

## 7. Контроль периода партии при существующих проверках

### Триггер

```text
trg_check_batch_quality_check_period
```

Таблица:

```text
production_batches
```

Событие:

```text
BEFORE UPDATE OF started_at, completed_at
```

Триггерная функция:

```text
check_batch_quality_check_period()
```

### Бизнес-правило

После регистрации проверки качества нельзя изменить временной интервал партии так, чтобы существующая проверка оказалась вне этого интервала.

Запрещается:

- устанавливать `started_at` позже существующей проверки;
- устанавливать `completed_at` раньше существующей проверки;
- удалять `started_at`, если для партии уже зарегистрированы проверки качества.

### Проверенные сценарии

Проверено:

- перенос `started_at` позже существующего `checked_at`;
- перенос `completed_at` раньше существующего `checked_at`.

Обе операции были отклонены.

## 8. Почему используются триггеры

Ограничения `CHECK` предназначены преимущественно для проверки значений одной строки.

Например:

```sql
CHECK (planned_quantity > 0)
```

не требует обращения к другим строкам или таблицам.

Реализованные бизнес-правила требуют:

- вычислять сумму нескольких строк;
- обращаться к связанным таблицам;
- проверять наличие связанных записей;
- сопоставлять значения нескольких сущностей.

Например, для проверки лимита заказа необходимо сравнить:

```text
production_orders.planned_quantity
```

с:

```text
SUM(production_batches.planned_quantity)
```

Поэтому такие правила реализованы с помощью триггерных функций PL/pgSQL.

## 9. Проверенные триггеры

В базе данных создано 6 пользовательских триггеров:

| Триггер | Таблица | Назначение |
|---|---|---|
| `trg_check_batch_planned_quantity` | `production_batches` | Контроль суммы партий |
| `trg_check_order_planned_quantity` | `production_orders` | Контроль уменьшения количества заказа |
| `trg_check_defect_quality_result` | `defects` | Запрет дефектов для `Passed` |
| `trg_check_quality_passed_without_defects` | `quality_checks` | Запрет `Passed` при наличии дефектов |
| `trg_check_quality_check_batch_period` | `quality_checks` | Проверка времени контроля качества |
| `trg_check_batch_quality_check_period` | `production_batches` | Защита периода партии |

Все перечисленные триггеры были проверены отрицательными тестами.

## 10. Нереализованное межтабличное правило

Пока не реализовано правило:

> Количество дефектов должно быть согласовано с объёмом продукции, прошедшей контроль качества.

Причина заключается в том, что текущая модель данных не содержит отдельного однозначного поля, отражающего количество продукции, предъявленной на контроль качества.

Перед реализацией этого правила необходимо уточнить бизнес-семантику `actual_quantity` либо расширить модель данных.

---

## 11. Итог

Триггеры используются для реализации межтабличных правил целостности, которые нельзя выразить стандартными ограничениями одной строки.

Реализован контроль:

- количества производственных партий относительно заказа;
- изменения планового количества заказа;
- согласованности результатов контроля качества и дефектов;
- временной согласованности проверок качества и производственных партий.

Всего создано и проверено 6 пользовательских триггеров.
