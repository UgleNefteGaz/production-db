# Дополнительные ограничения бизнес-логики

## 1. Назначение документа

Документ описывает дополнительные ограничения бизнес-логики, добавленные в базу данных производственного учёта.

Базовые ограничения структуры базы данных уже задаются в `db/schema.sql`:

- `PRIMARY KEY`;
- `FOREIGN KEY`;
- `NOT NULL`;
- `UNIQUE`;
- базовые проверки допустимых числовых значений и дат.

Дополнительные правила реализованы в файле:

```text
sql/constraints.sql
```

Их задача - предотвращать логически некорректные состояния данных, которые формально могли бы пройти базовые ограничения схемы.

Всего добавлено:

- 8 ограничений `CHECK`;
- 1 частичный уникальный индекс.

---

## 2. Период действия спецификации

Таблица: `specifications`

Ограничение:

```sql
ALTER TABLE specifications
ADD CONSTRAINT chk_specification_valid_period
CHECK (valid_to IS NULL OR valid_from IS NOT NULL);
```

### Логика

Если указана дата окончания действия спецификации `valid_to`, должна быть известна и дата начала её действия `valid_from`.

Допустимо:

```text
valid_from = 2026-01-01
valid_to = 2026-12-31
```

Также допустима спецификация без даты окончания:

```text
valid_from = 2026-01-01
valid_to = NULL
```

Некорректно:

```text
valid_from = NULL
valid_to = 2026-12-31
```

### Что предотвращает

Ограничение не позволяет сохранить период действия, у которого известен конец, но отсутствует начало.

---

## 3. Только одна активная спецификация продукта

Таблица: `specifications`

Ограничение:

```sql
CREATE UNIQUE INDEX uq_specifications_one_active_per_product
    ON specifications (product_id)
    WHERE status = 'Active';
```

### Логика

У одного продукта может существовать несколько версий спецификаций:

```text
1.0
1.1
2.0
```

Но в рамках принятой бизнес-модели одновременно активной должна быть только одна версия.

Например:

```text
Продукт SH500

Версия 1.0 -> Archived
Версия 1.1 -> Active
Версия 2.0 -> Draft
```

Допустимо. Но:

```text
Версия 1.1 -> Active
Версия 2.0 -> Active
```

не допускается.

### Почему используется частичный UNIQUE INDEX?

Обычное ограничение:

```sql
UNIQUE (product_id, status)
```

не подходит, поскольку запретило бы иметь несколько спецификаций со статусом `Draft` или `Archived`.

Частичный индекс контролирует уникальность только для строк:

```sql
WHERE status = `Active`
```

### Что предотвращает

Исключает ситуацию, когда для одного продукта одновременно используются две активные спецификации.

## 4. Плановый период производственного заказа

Таблица: `production_orders`

Ограничение:

```sql
ALTER TABLE production_orders
ADD CONSTRAINT chk_order_planned_period
CHECK (planned_end_at IS NULL OR planned_start_at IS NOT NULL);
```

### Логика

Если указано плановое окончание производства, должно быть указано и плановое начало.

Допустимо:

```text
planned_start_at = 2026-09-10 08:00
planned_end_at = 2026-09-10 16:00
```

Допустимо:

```text
planned_start_at = 2026-09-10 08:00
planned_end_at = NULL
```

Некорректно:

```text
planned_start_at = NULL
planned_end_at = 2026-09-10 16:00
```

### Что предотвращает

Не позволяет задавать окончание планового производственного периода без его начала.

Проверка того, что окончание не раньше начала, уже существует в основной схеме.

## 5. Завершение производственной партии требует начала

Таблица: `production_batches`

Ограничение:

```sql
ALTER TABLE production_batches
ADD CONSTRAINT chk_batch_completion_requires_start
CHECK (completed_at IS NULL OR started_at IS NOT NULL);
```

### Логика

Партия не может иметь фактическое время завершения, если отсутствует время её запуска.

Некорректное состояние:

```text
started_at = NULL
completed_at = 2026-09-10 15:00
```

### Что предотвращает

Исключает появление партий, которые формально завершились, хотя их начало производства не зарегистрировано.

---

## 6. Обязательные данные завершённой партии

Таблица: `production_batches`

Ограничение:

```sql
ALTER TABLE production_batches
ADD CONSTRAINT chk_completed_batch_data
CHECK (
    status <> 'Completed'
    OR (
        started_at IS NOT NULL
        AND completed_at IS NOT NULL
        AND actual_quantity IS NOT NULL
    )
);
```

### Логика

Если партия переведена в статус:

```text
Completed
```

у неё должны быть заполнены:

- фактическое время начала;
- фактическое время завершения;
- фактическое количество продукции.

То есть строка:

```text
status = Completed
started_at = NULL
completed_at = NULL
actual_quantity = NULL
```

не допускается.

### Что предотвращает

Не позволяет считать производственную партию завершённой при отсутствии основных фактических результатов производства.

---

## 7. Завершение операции требует начала

Таблица: `batch_operations`

Ограничение:

```sql
ALTER TABLE batch_operations
ADD CONSTRAINT chk_operation_completion_requires_start
CHECK (completed_at IS NULL OR started_at IS NOT NULL);
```

### Логика

Технологическая операция не может иметь время завершения, если время её начала не зарегистрировано.

Некорректно:

```text
started_at = NULL
completed_at = 2026-09-10 12:00
```

### Что предотвращает

Исключает логически невозможные временные интервалы выполнения производственных операций.

---

## 8. Обязательные данные завершённой операции

Таблица: `batch_operations`

Ограничение:

```sql
ALTER TABLE batch_operations
ADD CONSTRAINT chk_completed_operation_data
CHECK (
    status <> 'Completed'
    OR (
        started_at IS NOT NULL
        AND completed_at IS NOT NULL
        AND processed_quantity IS NOT NULL
        AND processed_quantity > 0
    )
);
```

### Логика

Если технологическая операция имеет статус:

```text
Completed
```

должны быть известны:

- время начала;
- время завершения;
- обработанное количество продукции.

При этом обработанное количество должно быть больше нуля.

### Что предотвращает

Не позволяет завершить производственную операцию без фактических данных о её выполнении.

---

## 9. Дата смены должна соответствовать времени её начала

Таблица: `shifts`

Ограничение:

```sql
ALTER TABLE shifts
ADD CONSTRAINT chk_shift_start_date
CHECK (started_at::date = shift_date);
```

### Логика

Поле `shift_date` определяет календарную дату смены. Поле `started_at` содержит точное время её начала.

Эти значения должны соответствовать друг другу.

Допустимо:

```text
shift_date = 2026-09-10
started_at = 2026-09-10 08:00
```

Некорректно:

```text
shift_date = 2026-09-10
started_at = 2026-09-11 08:00
```

При этом смена может завершиться уже на следующие сутки, поэтому аналогичное ограничение для `completed_at` не вводится.

### Что предотвращает

Исключает несогласованность календарной даты смены и фактического времени её начала.

---

## 10. Комментарий при проблемном результате контроля качества

Таблица: `quality_checks`

Ограничение:

```sql
ALTER TABLE quality_checks
ADD CONSTRAINT chk_quality_failure_notes
CHECK (
    result = 'Passed'
    OR NULLIF(BTRIM(notes), '') IS NOT NULL
);
```

### Логика

При успешной проверке:

```text
Passed
```

комментарий необязателен.

Если результат:

```text
Failed
```

или

```text
Conditional
```

необходимо указать причину или пояснение в поле `notes`.

Проверяется не только `NULL`, но и пустая строка.

Например, не допускаются:

```text
NULL
''
'   '
```

### Что предотвращает

Не позволяет регистрировать проблемную проверку качества без описания причины.

---

## 11. Почему не все бизнес-правила реализованы через CHECK?

Ограничение `CHECK` должно проверять данные текущей строки таблицы.

Некоторые бизнес-правила требуют анализа связанных строк из других таблиц.

Для таких правил обычный `CHECK` не подходит.

Примеры:

### 11.1. Сумма партий не должна превышать количество заказа

Необходимо сравнить:

```text
production_orders.planned_quantity
```

с суммой:

```text
production_batches.planned_quantity
```

для всех партий этого заказа.

Правило затрагивает несколько строк и две таблицы. Для его реализации может использоваться триггер.

### 11.2. Успешная проверка качества не должна содержать дефекты

Если:

```text
quality_checks.result = Passed
```

для этой проверки не должно существовать записей в:

```text
defects
```

Проверка требует обращения к другой таблице. Такое правило также может быть реализовано триггером.

### 11.3. Количество дефектов должно быть согласовано с объёмом продукции, прошедшей контроль качества.

Для контроля необходимо суммировать значения:

```text
defects.quantity
```

и сравнивать их с количеством продукции соответствующей партии.

Это межтабличное правило, поэтому простой `CHECK` для него недостаточен.

В текущей модели отдельное поле для количества продукции, предъявленной на контроль качества, отсутствует. Поэтому точное ограничение требует уточнения бизнес-семантики actual-quantity либо расширения модели данных.

### 11.4. Время проверки качества должно соответствовать производственной партии

Можно контролировать, чтобы время проверки качества логически соответствовало периоду выполнения партии.

Для этого необходимо сравнивать:

```text
quality_checks.checked_at
```

с:

```text
production_batches.started_at
production_batches.completed_at
```

Такое правило требует обращения к связанной таблице.

---

## 12. Итог

Дополнительные ограничения используются для защиты базы данных от логически некорректных состояний.

Реализованы правила для:

- периодов действия спецификаций;
- единственной активной спецификации продукта;
- плановых дат производственных заказов;
- фактических дат производственных партий;
- обязательных данных завершённых партий;
- фактических дат технологических операций;
- обязательных данных завершённых операций;
- согласованности даты смены;
- обязательного комментария при проблемном результате контроля качества.

Простые правила внутри одной строки реализованы через `CHECK`. Уникальность активной спецификации реализована частичным `UNIQUE INDEX`.

Правила, требующие анализа нескольких строк или нескольких таблиц, оставлены для реализации на уровне триггеров.
