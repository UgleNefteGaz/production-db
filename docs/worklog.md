### Реализованные межтабличные правила

1. Сумма `planned_quantity` партий не может превышать `planned_quantity` производственного заказа.
2. Плановое количество заказа нельзя уменьшить ниже уже распределённого по партиям количества.
3. Для проверки качества с результатом `Passed` нельзя зарегистрировать дефекты.
4. Проверку качества нельзя перевести в `Passed`, если для неё уже существуют дефекты.
5. `checked_at` проверки качества не может быть раньше `started_at` производственной партии.
6. Для завершённой партии `checked_at` не может быть позже `completed_at`.
7. Период производственной партии нельзя изменить так, чтобы существующие проверки качества оказались вне него.

### Отложенное бизнес-правило

Не реализован контроль количества дефектов относительно количества продукции, прошедшей контроль качества.

Причина: текущая модель не содержит отдельного однозначного показателя количества продукции, предъявленной на контроль качества.

Реализация правила требует уточнения бизнес-семантики `actual_quantity` либо расширения модели данных.

### Практические SQL-запросы

В `sql/queries.sql` реализованы следующие примеры.

#### 1. Регулярное выражение

Реализован поиск номеров производственных заказов, соответствующих формату:

```text
PO-YYYY-NNN
```

Например:

```text
PO-2026-001
PO-2026-010
```

Запрос исключает нестандартные номера, например:

```text
DEV-2026-001
TEST-ORDER-01
```

#### 2. INNER JOIN и LEFT JOIN

На реальных тестовых данных проверено влияние сочетания `INNER JOIN` и `LEFT JOIN`.

В базе специально присутствуют:

- продукт `CREAM50`, у которого нет спецификации;
- продукт `BALM250`, у которого есть спецификация, но нет производственного заказа;
- отдельные версии спецификаций без связанных заказов.

Это позволяет наглядно увидеть, какие строки сохраняются или исключаются при разных типах соединений.

#### 3. INSERT ... RETURNING

Реализован пример добавления продукта с немедленным возвратом созданной строки:

```text
INSERT ... RETURNING
```

`RETURNING` позволяет получить в том числе автоматически созданный `product_id`.

Тест выполняется внутри транзакции с `ROLLBACK`, поэтому добавленная строка не сохраняется.

При этом значение identity-последовательности после `ROLLBACK` назад не возвращается.

#### 4. UPDATE ... FROM

Реализован запрос, который переводит производственный заказ в `Completed`, если все связанные с ним партии имеют статус `Completed`.

Для демонстрации используется заказ `PO-2026-006`.

До выполнения запроса:

```text
PO-2026-006 -> InProgress

BATCH-009 -> Completed
BATCH-010 -> Completed
```

После `UPDATE ... FROM` заказ получает статус:

```text
Completed
```

Для проверки всех партий используется агрегатная функция `BOOL_AND`.

#### 5. DELETE ... USING

Реализовано удаление дефектов, связанных с тестовыми партиями.

Связь проходит через:

```text
defects
    -> quality_checks
        -> production_batches
```

Для демонстрации используется партия:

```text
TEST-BATCH-001
```

Удалённая строка выводится через `RETURNING`.

После демонстрации выполняется `ROLLBACK`.

#### 6. COPY

Реализован экспорт производственных заказов вместе с информацией о продукции в CSV-файл:

```text
/tmp/production_orders.csv
```

PostgreSQL вернул:

```text
COPY 12
```

Файл успешно скопирован из Docker-контейнера в рабочую директорию и проверен командой:

```bash
head production_orders.csv
```
